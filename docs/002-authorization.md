# 002 授权

授权决定谁可以发起工作，以及这些工作可以包含什么。本文档建立在 [001 领域模型](001-domain.md) 之上。

宿主（host）强制执行允许名单、规则和授权。消息、评论和引用的文档都是决定的输入；它们无法更改这些权限。

## 触发的两条路径

### 评估：决定是否开始工作

来源记录一条消息是否针对智能体：提及机器人或智能体账号为 `mention`，私聊为 `direct`。准入检查发送者和来源的策略：

- 允许名单上的人针对智能体发出的是明确请求。
- 某人在带有工单的线程上的后续消息遵循下面的规则。
- 其他人类消息使用它们接收范围的准入表。
- 来源机器人名单上的机器人可以产生推断候选，绝不可以产生明确请求。其他机器人不获准入。

### 订阅：继续现有工作

订阅线程上的每条消息都会作为上下文到达其已订阅的工单，包括来自机器人和 CI 的消息。这种投递绕过准入，不授予任何新权威。每个工单仍受其授权限制。

某人在工单自己的线程上发的消息，归该工单的执行器决定。当主 Session 把消息附加到工单时同样适用。当执行器拥有该消息时，它不经过评估，也不得到决定。每个执行器要么在工单范围内处理该请求，要么将其交回以在别处路由。

只要工单存活，这种所有权就持续，即使有人移除了它的订阅。它也覆盖一个已结束但未被某人停止、且正等待消息来恢复它的工单。

主 Session 会收到一条后续通知。当执行器拥有该消息时，主 Session 只能应人的请求停止工作；接单、附加、忽略和重新排队都会被拒绝。停止仍以如下所述的后续强度通过准入。

### 交回和释放后续消息

当消息请求的是工单范围之外的工作、或属于另一个工单时，执行器把它交回一次。工单保留其订阅。如果附加的线程无关，执行器交回它在那里拥有的消息。

只有在没有工单仍拥有该消息后，它才会进入一次新的评估。它的候选包含各执行器的理由。准入把它当作该线程上的一条普通消息来评判，主 Session 可以接单它、把它附加到别处或忽略它。交回一条工单并未拥有的消息（例如机器人消息、或某人已发给评估的消息）不会排队任何东西。

当工单结束时，它释放执行器未读取或未处理的后续消息。这些包括从未投递给执行器的消息，以及在其最后一次报告或回合结束之后投递、且它既未确认、未回答也未交回的消息。当没有其他工单拥有它们时，每条被释放的消息都进入评估。停止只结束被停止工单的工作。

被停止的工单不会再次把它的停止消息发给评估，除非另一个工单把它交回。停止它的主 Session 可以把该消息的其余部分作为新工作接单。

一个人可以从面板把一条被拥有的后续消息发给评估。如果主 Session 随后把它附加回一个活跃工单，执行器会再次收到它。当没有有效的判断覆盖该消息时，面板也提供重新评估。

### 仅上下文的订阅

执行器可以关注一个相关线程（例如另一个 Issue 或拉取请求）以获取上下文。它的消息到达工单，但不授予任何权威或后续强度。那里的人类消息不会使已结束的工单恢复，除非主 Session 附加了该线程的一条消息。主 Session 关于其他工作的注释也只是上下文。

到达不了任何工单的人类消息（包括其工单已被某人停止的线程上的消息）走评估路径。机器人消息独立于它们向已订阅工单的投递，也走该路径。

## 强度

| 强度 | 情形 |
| --- | --- |
| explicit 明确 | 名单上的人针对智能体，或在已有工单的线程上跟进；准入表某格设为明确请求 |
| inferred 推断 | 不在名单上的人在带工单的线程上跟进，除非其准入表对应格为明确；准入表某格设为推断候选；来源机器人名单上的机器人针对智能体、或在来源接收每条消息的地方到达的消息 |
| not admitted 不获准入 | 任何其他机器人的消息、准入表忽略的一切、以及接单模式为 `off` 时的所有推断情形 |

对不在名单上的人，明确的准入格即使在线程带工单时也优先，并且在所有接单模式下都有效。否则他们的后续是推断的，在 `off` 模式下不获准入。仅在上下文关注的线程上的消息使用准入表，而不是后续强度。

## 准入

每个来源的策略都有准入表。它的行是接收范围：

- **飞书：** 每个已配置的群聊、机器人收到提及的其他群聊，以及私聊。只有当飞书卡片上 **其他群** 设为 **仅 @** 时，其他群聊才会被接收。
- **GitHub：** 新 Issue、新拉取请求、评论和默认分支的 CI。

一行最多有三个格。每个格决定一条消息是成为明确请求、推断候选，还是什么都不是：

| 格 | 选项 | 默认 |
| --- | --- | --- |
| 在名单上、未针对智能体 | inferred 推断、ignore 忽略 | inferred 推断 |
| 不在名单上、针对智能体 | explicit 明确、inferred 推断、ignore 忽略 | ignore 忽略 |
| 不在名单上、未针对智能体 | inferred 推断、ignore 忽略 | ignore 忽略 |

未针对智能体的消息的格，只在来源接收每条消息的地方可用，例如设为 **全部消息** 的飞书群聊，或启用了全量接收开关的 GitHub 范围。CI 结果没有发送者，所以它的行只提供最后一格。机器人消息使用机器人名单，而不是这些格。

把“不在名单上但针对智能体”的格设为明确，能让该范围内的任何人通过提及智能体来请求工作。这对专门的客服群聊可能有用。推断候选仍取决于接单模式。后续通常绕过此表，但明确格仍授予明确强度。

准入表是策略版本的一部分。弱化某一格不会立即停止在其下接单的开放工单。它可以在这些工单恢复前重新校验时撤销它们的授权。

### 机器人和自动评审者

宿主把 GitHub App、以 `[bot]` 结尾的登录名和飞书机器人识别为机器人。来源可以列出诸如 `dependabot[bot]` 之类的机器人，其消息可以成为推断候选。它们必须要么针对智能体，要么在接收每条消息的范围里发帖。它们不能发起明确请求或停止工单。

使用普通账号的自动评审者对宿主而言算作人。它的评论到达已订阅工单并产生后续通知。团队提示词文本必须把这些账号标识为自动评审者。

## 路由候选

主 Session 用 `orchestrator_route` 路由明确候选。一次调用可以包含多个接单、附加、停止或忽略决定。每个条目独立处理：一个被拒绝的条目或缺字段不会阻止其他条目运行。

推断候选通常需要完整研判。有一个捷径：如果它的卡片明显不触及任何启用的规则，例如普通聊天或无关讨论，主 Session 可以直接忽略它。决定记录 `ignoredFromCard` 以区别于规则研判。主 Session 在其策略提示词部分读取启用的规则。

接单推断候选始终需要研判。直接接单会拒绝一个准入未将其判定为明确的触发。

## 接单模式和规则

接单模式是策略的一部分：

| 模式 | 效果 |
| --- | --- |
| `off` | 任何推断的东西都不成为候选，例如未针对智能体的消息、机器人消息，或不在名单上的人的后续 |
| `observe`（默认） | 推断候选被研判；正向研判被记录为标注“would accept（会接单）”的忽略，什么都不接单 |
| `auto` | 对推断候选的正向研判接单它 |

明确请求在所有模式下都有效。从 `observe` 开始，在审查了已记录的决定后切换到 `auto`。每次研判对每条启用的规则恰好判断一次，无论是否匹配。主动接单需要至少一条匹配的规则。

每条规则描述一种主动工作。工单的授权记录匹配的规则，其执行器收到它们的名称和说明。

对那个工单，规则的流程和沟通要求覆盖默认值。沉默规则可以抑制确认；评审规则可以指定所需的评审者和合并前的批准。适用于每个工单的要求应放在团队提示词部分。

## 策略版本

规则、接单模式和每个来源的策略构成策略版本。每个授权都记录它所依据的版本。

版本变更会丢弃正在运行的评估并重新排队其触发。它还会向每个受影响的活跃工单发送一条策略变更输入。输入说明是否：

- 某条匹配的规则变了，包括它的新文本，或不再适用；
- 请求者不再能发起工作；或
- 主动工作不再被接单，例如模式从 `auto` 变了。

未受影响的工单不收到通知。变更不会立即撤销活跃工单的授权。

来源配置独立于策略。它控制什么进入系统：读取哪些群聊，以及某范围是接收所有消息还是仅提及。授权记录其来源和接收范围。恢复需要来源仍监听该线程，但不要求它仍接收那里的每条消息。

当来源关闭时，回复会等待。如果来源不再监听其目的地，它们会被丢弃。

关于执行器可以对自己的结果做什么的条件（例如何时可以合并）不决定谁可以授权工作。它是智能体指令的一部分，而不是策略的一部分。

## 恢复和停止

已结束的工单保留其授权。某人在其自己的线程之一上发的消息可以在没有新评估或决定的情况下恢复同一工作，无论谁发的。机器人和 CI 不会唤醒已结束的工单。执行器决定请求是否符合范围，如果不符合则结束该回合。

只有三种操作改变授权：接单创建它，人的停止撤销它，重新校验失败撤销它。被某人停止的工单保持已结束状态，不再接收任何东西。在那里请求的工作需要新的接单。

### 恢复前的重新校验

来源必须仍监听原始线程。其余检查取决于授权依据：

- 明确后续的授权通过。
- 推断授权需要 `auto` 模式，且其匹配的规则仍启用。
- 由表某格准入的授权，必须在今天的表和发送者成员关系下仍至少获得其原始强度。因此，把发送者从名单中移除可以撤销一个通过“名单发送者”格接单的授权。
- 机器人的授权要求该机器人仍在来源的机器人名单上。推断的表授权和机器人授权还需要 `auto` 模式和启用的匹配规则。
- 其他授权要求发送者仍在来源的允许名单上。

如果重新校验失败，工单保持已结束状态，不处理任何等待的消息。每条消息都被视为没有到达任何工单；如果没有其他工单拥有它，它就进入评估。主 Session 不会被告知它到达了某个 worker。这在处理暂停之后同样适用。附加到工单被拒绝，进一步工作需要新的接单。

- **某人在线程里说“停止”是一条普通触发，** 由评估决定停止。执行器不能声明某人要求它停止。
- **面板中的停止是一个命令。** 它直接作用于工单，被记录为手动停止。
- **等待条件属于来源。** 诸如“N 小时无人认领”之类的条件会是一个自己等待并再次检查的来源；评估从不等待。

## 当评估未完成时

时间限制从候选到达主 Session 时开始。等待投递的时间不计入，未投递的候选永不过期。

过期的评估会重新排队其触发以再次尝试。连续重试两次后，第三次过期记录 `unavailable`。研判失败也记录 `unavailable`；稍后的触发可以开始新的评估。策略变更或针对过时策略做出的决定记录 `unavailable`，并在当前版本下立即重新排队该批次。

`evals` 健康条目报告最近一小时未解决的 unavailable 决定。`scripts/dsh-superagent status` 包含该错误。

只有当 unavailable 决定不到 24 小时、仍是其线程上的最新决定、未被驳回、且该线程既未排队也未在评估中时，面板才会请求人的关注。人可以再次评估该触发或驳回该问题。
