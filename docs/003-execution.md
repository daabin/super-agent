# 003 执行

本文档跟随一个已接单的工单走过执行、交付和恢复。它建立在 [001 领域模型](001-domain.md) 和 [002 授权](002-authorization.md) 之上。

## 工单阶段

每个打开的工单都有一个阶段，由它正在等待什么决定。从上到下读表格；第一个匹配的行生效。

| 阶段 | 条件 | 面板标签 |
| --- | --- | --- |
| person / delivery | 向执行器 Session 投递输入失败；2 秒后重试，随后延迟翻倍直至一分钟，一次成功、一次新派工或工单结束会清除它 | Input undelivered（输入未投递） |
| person / answer | 它有 Attention（待人工决定） | Awaiting answer（等待回答） |
| person / review | 最新报告为 `ready` | Awaiting review（等待评审） |
| person / blocked, failed | 最新报告为 `blocked` 或 `failed`，且此后没有人的消息到达工单 | Blocked · Failed（受阻 · 失败） |
| working / queued | 没有派工，或有一个待启动的派工 | Queued（排队中） |
| idle | 最新报告为 `waiting`，或派工已结束 | Waiting for a Trigger（等待触发） |
| working | 其他一切 | Working（工作中） |

`person` 阶段意味着工单没有人的输入就无法继续。一条新的人类消息会把 `blocked` 或 `failed` 的工单释放给它的执行器，因此它移动到下一个匹配的阶段，通常是 `working`。

`idle` 工单已经结束回合而没有未决问题。订阅线程上的触发可以继续它。

## 执行器

每个工单得到一个名为 `worker-<ticket id>` 的执行器 Session，以及一个以工单短名命名的目录。目录创建在配置的执行根目录下，默认是 `<stateDir>/work`。

执行器 Session 以运营者的 OS 用户身份、无需批准地运行命令。它们的 `dsh-superagent-worker` 预设包含工作所需的工具，并在 5 秒后把前台 shell 命令移到后台作业。这让 worker 能在下一步接收新消息，而不是等待一个长命令结束。

主 Session 使用 `dsh-superagent-router`，具有相同的 5 秒 shell 和作业等待限制，以及用于路由的较小工具集。Session 保留创建时所选的预设。worker 子智能体使用 DeepSeek Harness 的 `standard` 预设。

### 后台工作和 worker 槽位

当回合结束时 shell 作业或子智能体仍在运行，工单保留其 worker 槽位并保持工作中。它不会被报告为等待，主 Session 也不会收到等待报告。完成的作业或子智能体在同一槽位里用其结果唤醒执行器。一旦回合结束且没有后台工作，执行器正常报告等待。

每个回合之后，后台工作最多有 30 分钟完成。到该上限时，shell 作业被终止，工单被报告为等待。报告包含执行器的最后话语，以及哪些作业被终止、哪些子智能体仍活跃。子智能体被允许继续。执行器在下一个回合读取被终止作业的结果。

向人交接会立即释放槽位，并使报告保持有效。这适用于 `ready` 报告或一个问题之后（除非此后有另一条输入到达），也适用于任何 `blocked` 或 `failed` 报告之后。

交接时，子智能体停止。shell 作业（例如为评审而提供的服务器）可以继续，直到派工结束。它们不占槽位，且不受 30 分钟限制，包括在之后的回合之后。它们的完成不会唤醒执行器；它在下一个回合读取结果。

一个人也可以直接在执行器 Session 里写消息来启动一个回合。它的后台工作遵循同样的规则。

当派工结束时，其 shell 作业被终止而不唤醒 Session。其子智能体被释放，它们唤醒的任何完成回合都被丢弃。替代派工及其等待的输入在该关停完成后开始。

在 DeepSeek Harness 进程内停止或重启插件使用相同的关停路径。尚未纳入 Session 历史的输入被保留。关停最多等待每个 worker 的后台工作 10 秒；进程重启则彻底结束该工作。一个在忙碌中被中断的派工会带着恢复说明重新开始。

worker 子智能体，包括嵌套的，使用 DeepSeek Harness 的 `standard` 预设和 worker 的权限。它们只保留 worker 允许的工作工具，并在工单结束时失去这些工具。在 `standard` 下，shell 命令 60 秒后移到后台。子智能体的作业在它结束时被终止。

### 准备工单目录

在第一次派工之前，如果工单目录不存在，prepare 命令会在执行根目录下用 `sh` 运行一次。它有十分钟完成。没有 prepare 命令时，worker 在一个空目录里开始。

命令失败会使工单失败并记录其输出。重试、或某人发在工单线程之一上的消息，会再次尝试准备。典型的命令使用 `git worktree` 创建检出。当拉取请求分支的最后一段路径与工单短名匹配时，该拉取请求属于该工单。

### 并发

工单从启动开始（包括准备）就持有一个 worker 槽位，或者从唤醒其空闲执行器的投递开始持有。它在整个活跃回合期间也持有槽位。

配置的并发限制适用于这些槽位，另外有一个额外槽位给某人的消息或状态请求。当普通槽位已满时，这种唤醒可以使用额外槽位，并在新启动之前占用下一个空闲槽位。因此，新工作无法阻止某人继续现有工单。

其他输入，例如 CI 结果，等待普通槽位。启动在 `working / queued` 中等待，直到有槽位空闲。启动并发运行，所以一个慢的 prepare 命令只延迟它自己的工单。

### 执行变量

prepare 命令和执行器指令收到相同的执行变量。命令读取环境变量；执行器在其提示词中读取它们的值和描述。它们都不含凭据。

| 变量 | 注册方 | 值 |
| --- | --- | --- |
| `DSH_SUPERAGENT_DIR`、`DSH_SUPERAGENT_NAME`、`DSH_SUPERAGENT_TICKET` | 执行器 | 工单的目录、短名和 id |
| `DSH_SUPERAGENT_BLOCKED_COMMANDS` | 执行器 | 执行器不得运行的命令 |
| `DSH_SUPERAGENT_GITHUB_REPOSITORY` | GitHub | 来源监听的仓库，`owner/name` |
| `DSH_SUPERAGENT_GITHUB_ACCOUNT`、`DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL` | GitHub | 智能体账号及其提交邮箱 |
| `DSH_SUPERAGENT_GITHUB_NUMBER`、`DSH_SUPERAGENT_GITHUB_PR_HEAD` | GitHub | 启动工单的 Issue 或拉取请求，以及当它是拉取请求时的 head ref |
| `DSH_SUPERAGENT_FEISHU_BOT`、`DSH_SUPERAGENT_FEISHU_CHAT` | 飞书 | 机器人，以及启动工单的群聊 |

工单特定值来自它的目录和起始触发。其他值来自当前部署设置。只有面板能更改执行环境设置；发给主 Session 的文本无法更改已配置的 shell 命令。

worker 通过智能体账号的 `gh` 访问 GitHub，通过机器人的 `lark-cli` 访问飞书。被阻止的命令按名称调用时失败。

这些包装器和目录建立的是默认值，不是安全边界。worker 仍可以通过绝对路径执行程序。

## 合并

自动合并由 **交付要求** 提示词约束。宿主没有针对合并的决策逻辑。

默认情况下，执行器绝不以智能体账号启用自动合并：GitHub 会把合并归因于启用它的人。交付要求必须指定另一个账号的 CLI 用于合并。没有它，由人来合并拉取请求。

默认指令只允许为工单打开的拉取请求启用自动合并，且当它已就绪、所需批准覆盖 head 提交、且新增加删除总计少于 200 行时。在推送另一个修订版之前，执行器会撤回自动合并。

没有正文的评审（例如批准）也会作为触发到达，并可以唤醒等待评审的执行器。这些指令约束的是智能体，不是 GitHub 的合并规则。要强制执行批准，请在分支保护里要求它们并驳回过期的批准。省略合并 CLI 或移除自动合并段落，即要求手动合并。

## 工单如何结束

- **就绪但没有拉取请求：** `ready` 报告以完成状态结束工单。
- **无事可做：** 发现没有需要人来行动的工作的执行器，例如一个不复现或被取代的请求，报告 `dropped`。工单在没有消息的情况下结束，除非匹配的规则要求一条，某人稍后在其线程上发的消息会使其恢复。

### 拉取请求

一旦工单的执行器报告它启动的拉取请求，工单就跟随该拉取请求。它也会跟随从它的分支打开的每个拉取请求（一旦执行器报告，或被 GitHub 来源发现）。重新打开的拉取请求会被再次跟随。

当它打开的拉取请求都没有保持打开时，工单完成。如果它一个都没打开，则它跟随的所有拉取请求都必须关闭。然后它以上次相关关闭的结果结束，并保留其订阅，允许稍后的人类评论使其恢复。

只要恢复、重试或恢复中的工作尚未完成，关闭就不会结束工单。如果执行器确认或回答了一条它拥有的后续消息，但在读取该消息后尚未产生非 progress 报告、或尚未结束回合，它也等待。之后，一旦满足同样的拉取请求完成规则，`ready` 报告就结束工单。

聊天渠道收到一条关于拉取请求结果的最终通知。GitHub 已经在拉取请求本身上显示结果。移除工单对拉取请求的订阅也会停止它跟随该拉取请求。

因此，“Awaiting review（等待评审）”意味着带有拉取请求的 `ready` 报告。

### 后续和上下文线程

执行器决定其工单自己线程上的人类后续。它处理范围内的请求，交回超出范围或属于另一工单的请求。一旦没有执行器拥有该消息，它就成为主 Session 的候选。否则主 Session 只能应人的请求对后续采取停止工作的行动。

一条输入在 Session 把它纳入一个步骤、并随后报告或结束回合后，才计为已读。当工单结束时，未被确认、回答或交回的未读消息返回评估，如 [002 授权](002-authorization.md) 所述。已读但未采取行动的消息（例如感谢）不会返回。

仅为上下文关注的线程仍投递消息，但不给工单人类后续的所有权，也不恢复已结束的工单。这些消息可以独立地被研判。

只要有活跃工单订阅，来源就轮询已订阅线程；并且在最后一个触发与订阅工单结束二者中较晚者之后的两周内也轮询。此后，消息只通过普通接收到达：GitHub 通知或飞书实时事件。

## 失败和恢复

### 执行器受阻或失败

当执行器 Session 报告 `blocked` 或 `failed`，或启动失败、出错（这记录 `failed`）时，工单不接收自动输入。

模型提供商或网络的偶发失败，HTTP 408、429 或 5xx，或连接被拒绝、重置或超时，会先重试，三次并逐步退避：启动会再次运行，回合失败的 worker 被要求继续；失败的 prepare 命令不再重试。

一旦失败，CI 和机器人消息被记录在它上面，但不投递，也不唤醒 Session。

它的工具保持可用，所以一个人可以直接在 Session 里继续。

启动失败的不会自行重试。

某人的消息、一份既非 `blocked` 也非 `failed` 的后续报告、或一次重试，会结束该挂起状态。

它是从存储的报告和输入中恢复出来的，所以重启后仍保留。

### 重试

当打开的工单处于 `person / delivery`、`person / blocked` 或 `person / failed` 时可用：一次新派工（重新启动其 worker 并接收等待的输入）是每种情况的补救措施。

一旦某人的消息到达受阻或失败的工单，执行器就有了该消息，因此工单显示为工作中，或当失败的启动再次开始时显示为排队中，并且不提供重试，除非投递该消息失败。

重试结束当前派工，并在同一执行器 Session、目录、分支和拉取请求中启动一个新派工。

执行器模型只在创建 Session 时应用；现有 Session 保留其模型。

### 重启

运行中的派工以“host restarted（宿主已重启）”结束，新的派工以一条恢复说明开始，该说明告诉执行器在重复任何对外操作之前检查其目录、git 历史和 GitHub，最旧的工单优先。

处于等待、就绪、受阻或失败的派工保持原样，除非在该报告之后有输入到达它们，那样它们也会再次开始。

Session、目录、订阅、待处理消息和下文存储的工作在重启后保留，每个执行器 Session 纳入其历史的消息记录也保留——一个步骤在认领消息之后、在其模型调用之前做这件事：被重启切断的回合所接收的消息，在报告或回合结束随之而来时计为已读；而一个步骤已认领、但在计入历史之前被取消或出错切断的消息，计为未读。

重试或重启会再次给新派工那些投递给它所替代的派工、但其执行器 Session 未接收的消息——取消或被切断的步骤可能已丢弃它们；仍留在 Session 里的副本（由重启保留，或在崩溃后持久化）会在新派工的第一条消息之前被取出，因此新的投递是唯一的副本。

### 存储的工作

dsh-superagent 在做出决定之后所做的事——例如把候选、后续或报告中继给主 Session，启动派工，或投递输入——都是先存储、后执行。

失败的中继或投递（例如无法到达其 Session 时）在 2 秒后重试，随后延迟翻倍直至一分钟；启动失败会使它的工单失败，除非如上所述是偶发失败。

每种工作只有在某一条目连续失败三次后，才在概览的系统问题中报告错误；输入投递失败则显示在它的工单上。

给主 Session 的中继保持顺序，通知也是如此；失败的一条会挡住同类的后续条目。

### 来源失败

GitHub 来源独立读取每个 Issue、拉取请求和线程：失败的读取把错误保留在其线程上，在下一次轮询时再次读取，并计入来源的错误，来源默认在连续三次轮询失败后报告它；任何成功的轮询都会重置计数。

当智能体失去对私有仓库的访问时，GitHub 也会回答 404，所以 404 会被重试。

一个读取持续失败的被通知 Issue 或拉取请求，在首次读取失败一天后被丢弃；当 GitHub 报告它已删除时立即丢弃。之后它不再使轮询失败，其线程保留错误，来源的状态会点出它。

它的读取位置保持不变，所以稍后的通知或对其线程的轮询会读取失败读取所错过的东西。

飞书事件消费者报告每次失败，订阅话题的轮询把每次失败保留在其线程上。

GitHub 列表或飞书页面中的畸形条目被跳过，来源的状态会计数它。

### 渠道失败

外发消息被存储并作为存储的工作发送，从 5 秒起以翻倍直至 300 秒退避重试。

工单发给一个会话的消息按排队顺序发出，因此它的确认在其后续回答或结果之前：当同一工单发给同一会话的更早消息尚未发出时，消息会等待，直到那条更早消息连续失败三次并显示为问题。

其他工单的消息，以及无工单的消息，不等它。

有失败尝试的消息是一个系统问题，直到它发出或被撤回。

只有当来源不再监听该会话，或来源回答说该会话永远无法接收它时，消息才被丢弃；来源关闭时它等待。

对于 GitHub 上已删除的 Issue 或锁定的会话，以及飞书上已撤回或飞书已找不到的消息，来源会这样回答。

对已不存在的评审评论的回复，改为发到拉取请求的会话。

被丢弃的消息保留其记录，包括何时、为何被丢弃以及它服务于哪个工单，因此它永远不会再次排队；被丢弃的确认读作已丢弃，而非已发送。

### 暂停处理

停止分派、新评估、评估超时、输入投递和回复；已在进行的启动会等待，直到处理恢复。

来源继续记录触发，运行中的执行器回合不被中断。

某人发给已结束工单的消息等待：暂停后的第一轮通过会恢复该工单，如果它的授权在当时的策略下仍成立。

进行中的评估在暂停期间不过期；它的截止时间随暂停时长向后移动。

### 无效配置

一个其种类拒绝的已存储来源配置会禁用该来源实例。
