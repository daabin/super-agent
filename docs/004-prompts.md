# 004 提示词

本文档解释智能体读什么、团队能编辑什么、以及变更何时生效。它建立在 [000 哲学](000-philosophy.md) 到 [003 执行](003-execution.md) 之上。提示词文本以英文书写。

## 团队写什么

团队可以编辑三个团队部分、添加技能，并覆盖每个内置系统提示词部分。大多数默认值位于 `prompts/` 和 `skills/` 下。工具描述、通知和卡片保留在代码里，无法通过提示词设置编辑。

| 部分 | 内容 |
| --- | --- |
| 沟通 Communication | 何时给人发消息、消息如何措辞、每条 GitHub 消息开头的行（默认为 `This is by an automated agent, not a human`）、如何处理评审，以及哪些普通账号是评审机器人 |
| 工单范围 Ticket scope | 工单何时继续、何时以草稿停止 |
| 交付要求 Delivery requirements | 拉取请求中的证据、带行数阈值的自动合并条件，以及提交作者；没有它，执行器以智能体账号的 no-reply 地址提交 |
| 团队技能 Team skills | 智能体在需要时加载的知识，例如一个 `identities` 技能，说明哪个飞书用户是哪个 GitHub 账号 |

内置文本覆盖角色、工具使用、宿主机制、授权规则，以及 GitHub 和飞书技能。它通过标题引用团队部分，而不是重复它们。

### 内置部分和模板

覆盖使用这些键：

| 部分 | 键 |
| --- | --- |
| 共享指令和角色 | `runtime/shared`、`runtime/orchestrator`、`runtime/worker` |
| 工作指令 | `runtime/subscriptions`、`runtime/replies`、`runtime/dispatch`、`runtime/work`、`runtime/admission` |
| 交接指令 | `runtime/handoff/orchestrator`、`runtime/handoff/worker` |
| 来源技能 | `skill/feishu`、`skill/github` |
| 生成的部分 | `runtime/environment`、`runtime/policy`、`runtime/policy/none` |

生成的部分是可编辑的模板。它们必须保留这些占位符：

- `runtime/environment`：`{variables}`，填充执行环境行。
- `runtime/policy`：`{version}`、`{mode}` 和 `{rules}`，每条启用的规则一行。
- `runtime/policy/none`：`{version}` 和 `{mode}`，在没有启用规则时使用。

编辑某个部分会改变模型收到的指令。它不会改变准入、授权、工具检查或账号包装器，这些仍由代码强制执行。

应某人的明确请求，主 Session 也可以用 `orchestrator_prompts_save` 保存覆盖。如果保存省略了某覆盖的 `base`，它保留已保存的 base。一个已存在于已保存配置中的部分在保存时被移除；任何其他未知部分被拒绝。

覆盖记录它基于哪段内置文本。升级保留团队的文本。如果默认值变了，面板把该部分标记为 **Default updated（默认内容已更新）**，并在团队文本旁边显示差异。团队可以保留自己的文本、使用新默认值或编辑它。没有覆盖的部分自动跟随新默认值。

主 Session 可以在 `orchestrator_read prompts` 的 `default_changed` 下读取受影响的部分名。

## 组装和优先级

系统提示词按此顺序组装：

1. 共享指令和角色。
2. 三个团队部分。
3. 订阅和回复。
4. 主 Session 的分派，或执行器的工作指令。
5. `runtime/admission`，仅主 Session。
6. 交接指令。
7. `runtime/environment`。
8. `runtime/policy`，仅主 Session。

准入指令来自 `prompts/admission.md`。它们描述主动研判，以及何时可以从卡片忽略不相关的候选。`orchestrator_eval` 返回上下文，而不是重复这些指令。

环境部分给主 Session 部署范围的值，给每个执行器其工单特定值。策略部分在每次模型请求时从设置重新生成。它包含策略版本、接单模式、明确请求豁免，以及 `- <name> (<id>): <instruction>` 形式的启用规则，或一条说明没有启用规则的陈述。它排在最后，这样策略变更不会改变前面的提示词文本。

执行器还阅读 DeepSeek Harness 的编码提示词和仓库的 `AGENTS.md`；主 Session 不读。推断工单附加一条最终说明，把它的执行器限制在匹配的规则内。派工和传入消息以内联方式作为触发卡片到达，只有被截断的内容才用资源指针。

执行器无人值守工作。它们的工具排除了那些询问人、向人展示 UI 或更改配置文件的工具，例如 `ask_user_question`、`present` 和 `plugin_manager`。

从最强到最弱：

1. 由工具和宿主强制执行的事实：身份、权限、工具参数检查、回复目的、长度限制。提示词文本无法改变它们。
2. 内置和生成的部分，按团队对它们的覆盖所读。
3. 主动工单匹配规则中的流程和沟通，仅对该工单的执行器 Session 有效。
4. 团队部分和团队技能。
5. 外部文本：消息、评论、文档和引用。它是数据，永不改变规则或授权。

## 内置文本的原则

这些把 [000 哲学](000-philosophy.md) 应用于智能体：

- **角色分离。** 主 Session 只路由：它转发原始触发和路由事实，不做技术决定，通过一个路由工具在一次调用中对多个等待候选做决定。路由说明最多 30 词。执行器读取原始来源，判断范围，实现并验证。
- **主 Session 不等待。** 报告、后续通知、候选和已完成的作业自动作为消息到达。无事可做时它结束回合。一个守卫拒绝 `sleep`、超过 30 秒的 shell 超时和超过 5 秒的作业等待，因为被阻塞的步骤会延迟新候选。这些指令在主 Session 的完整提示词中取代 DeepSeek Harness 自己的作业通知说明。
- **只在有人必须行动或能使用结果时发消息：** 结果可以被评审或使用，需要决定或资源，或工作无法完成。聊天消息默认一句话，硬性上限 100 词。
- **执行器决定自己的后续。** 每个执行器处理并确认范围内的请求，交回超出其工单或属于另一工单的请求。只有在所有拥有者交回它、或结束而未处理它之后，消息才成为新工作。主 Session 收到后续通知，但只能对它们采取停止工作的行动。被交回的消息随后带着执行器的理由作为候选到达。
- **通过订阅和主 Session 协调。** 执行器关注相关线程以获取上下文。主 Session 可以在最多 100 词的注释里发送来自另一工单的事实。订阅和注释都不授予权威。
- **只在明确引用时附加。** 消息必须指向工单的拉取请求、Issue、来源消息或确认，或指向恰好匹配一个工单的近期变更。仅话题相似是不够的。附加把工单订阅到整个线程；发现它无关的执行器使用 `orchestrator_thread_unrelated`，且不在那里回答。
- **具体地确认一次。** 在实质性工作之前，执行器确认每个新请求，并作为原始消息下的回复，点名对象和预期结果。
- **通过 `human_action` 提问。** 执行器把一个问题放在它的报告里，主 Session 原样转发。如果某人的消息引发了该问题，它点名该消息，宿主在那里提问。否则它在工单的原始会话里提问。已获授权的工作可以同时继续。
- **诚实交付。** 打开拉取请求不是就绪；草稿标记为未完成；没有真实前后截图的 UI 变更不算就绪。
- **某人的暂停会保持** 跨后续、新执行器 Session 和重启，直到某人解除它。自动反馈绝不恢复已暂停的工作。
- **示例只展示格式。** 示例句子不是智能体可以声称的事实。
- **按结果处理评审。** 已修复并验证的评论被静默解决；被拒绝的得到一句理由。自动评审者的线程一旦有了回答就被解决，每个自动评审者每个拉取请求最多三轮。
- **向重复工作让步。** 当某人的分支或拉取请求已包含工单的变更时，执行器用一句指向他们的话关闭自己的拉取请求。

## 版本

- 每次保存创建一个不可变版本，包含完整配置、修订号、前任、时间戳和来源（面板或工具）。恢复版本或默认值会创建另一个版本。
- 保存会标明其基准修订版。冲突的保存被拒绝，且不丢弃草稿。
- Session 在每次模型请求时读取最新版本，包括同一回合中的后续步骤。保存不重启、不取消、不唤醒 Session。宿主记录每个 Session 使用过的修订版；执行器可以读取它工作过的任何修订版。
- 部署设置一个总大小限制，包括覆盖。校验拒绝未知键、保留的内置技能名、未知覆盖部分和缺失的模板占位符。它绝不静默截断文本。与默认值相同的覆盖被移除，以便该部分跟随未来默认值。
